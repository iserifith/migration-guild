## Summary

Five user stories close the Critical/High-severity defects a black-box onboarding re-test (#148) found against `origin/dev` @ `7db91e9`: (1) the shipped tarball omits `migration/package.json`, `migration/package-lock.json`, and `migration/registry_schema.sql`, so a tarball-only consumer's documented `cd migration && npm install` has nothing to install from and every `guildctl` command crashes on `Cannot find module 'dotenv'`; (2) `npm run build:dist` shells out to `npx tsup` with `cwd: migration/`, which silently requires `migration/node_modules` that DEVELOPMENT.md's "Build the repo" section never tells a maintainer to create; (3) `DEFAULT_GUILD_CONFIG` in `migration/guildctl/config.ts` seeds a personal `https://example-private.invalid/v1` / `EXAMPLE_PRIVATE_API_KEY` profile plus four DashScope-pointing profiles, none of which any shipped doc names, so a fresh `guildctl init` hands a doc-following user a `doctor` failure on a credential they were never told to set; (4) `checkHarness` in `migration/guildctl/harness.ts` reports the same generic `(<command> is missing or unreachable)` wording whether the adapter file is truly absent or present-but-failing (e.g. the wrapped Copilot CLI itself isn't installed), sending the user hunting for a file that is fine; (5) five documentation inconsistencies (a stale `guildctl.config.json` comment, an undocumented `--legacy-path` flag, two different pipeline command forms across README.md/GETTING-STARTED.md, and unguarded piped-stdin EOF in the setup wizard) compound the onboarding-time cost. All five stories are scoped to the packaging script, one config module, one harness module, and documentation — no registry, claims, evidence-gate, arbitration, audit-rule, or UI code changes (FR-014).

Research during this plan surfaced two corrections to the spec's own citations, both handled in the Technical Approach sections below rather than blocking the plan: FR-014's `setup.ts:189` citation for a `guildctl.config.json` copy reference does not exist in current `setup.ts` source (that line is `readline.createInterface(...)`, correctly cited separately in the Assumptions section at `setup.ts:189-219`); the actual dead copy reference lives only in the stale compiled artifact `package/setup.js:189`, which self-heals the next time `npm run build` recompiles `setup.ts` (already free of the reference). And FR-007's "11 test files (~103 matches)" grep-surface estimate is an undercount against the current tree: a case-insensitive grep for `DEFAULT_GUILD_CONFIG|private-relay|PRIVATE_RELAY|pvt/|dashscope` over `migration/test/*.test.ts` matches 15 files / 164 lines (the case-sensitive variant matches 13/160, missing two `DASHSCOPE_API_KEY`-only fixtures whose all-caps literal the case-sensitive `dashscope` term doesn't catch) — of these, 9 files need genuine value-assertion edits; the rest (`evidence-runtime.test.ts`, `verification-state.test.ts`, and four more) use `DEFAULT_GUILD_CONFIG` structurally or `EXAMPLE_PRIVATE_API_KEY`/`DASHSCOPE_API_KEY` only as an arbitrary secret-shaped literal in a redaction fixture, not as an assertion on `DEFAULT_GUILD_CONFIG`'s actual values, so they need no code change but should stay in the regression-run scope for completeness. `tasks.md`'s T011–T020 is the authoritative per-file breakdown.

## Technical Context

**Language/Version**: TypeScript (Node 18+; developer machine runs a current Node), compiled via the existing `migration/` tsup toolchain (`migration/tsup.config.ts`); tests run on the built-in `node:test` runner (`node --import tsx --test test/*.test.ts`, `migration/package.json`). The packaging script itself (`scripts/build-dist.mjs`) is a root-level ESM `.mjs` file run directly by `node` (root `package.json`'s `build:dist` script), not compiled.

**Primary Dependencies**: `migration/package.json`'s runtime `dependencies` — `dotenv` (17.4.0), `better-sqlite3` (12.8.0), `commander` (12.1.0), `yaml` (2.8.1), `@modelcontextprotocol/sdk` — none of which `migration/tsup.config.ts` bundles (both `tsup` entries in that file have no `noExternal`/bundling of these; they resolve at runtime from `node_modules`), which is exactly why the tarball's `migration/` needs a real `package.json` + `package-lock.json` to `npm install` against (US1).

**Storage**: SQLite registry (`better-sqlite3`); no schema change. `migration/registry/db/schema.ts`'s `resolveSchemaPath()` (lines 5–19) walks up from `__dirname` looking for `registry_schema.sql`, falling back (line 18) to `path.resolve(__dirname, "..", "..", "registry_schema.sql")` — from a packaged `migration/registry/dist/db/`, that resolves to `migration/registry_schema.sql`, so once US1 ships that file at the tarball's `migration/` root, the walk-up finds it with zero code change to `schema.ts`.

**Testing**: `node:test`, `migration/test/*.test.ts`. US1's regression test follows the existing `migration/test/build-dist-docs-skip.test.ts` pattern (stage a self-buildable temp kit root, run the real `scripts/build-dist.mjs` against it via `execFileSync`, extract the resulting tarball, assert on its contents) rather than a lighter-weight `assembleTarball()`-only invocation, because `assembleTarball` is not exported and the existing precedent already solves staging a runnable `migration/node_modules` + `migration/ui/node_modules`.

**Target Platform**: Linux/macOS/Windows CLI (`guildctl`, `registry`) plus the packaging script, which already special-cases Windows (`resolveCommand` at `scripts/build-dist.mjs:18-24`, `shell: true` at line 33) — any US2 install step must reuse `run()`/`resolveCommand`, not a new spawn call.

**Project Type**: CLI runtime library (`migration/guildctl/`, `migration/registry/`) + its packaging script (`scripts/build-dist.mjs`) + its regression suite (`migration/test/`) + shipped documentation (`README.md`, `GETTING-STARTED.md`, `DEVELOPMENT.md`, `.env.example`, `package/.env.example`).

**Performance Goals**: None new. FR-001 adds ~63 KB (`package-lock.json`) + ~32 KB (`registry_schema.sql`) to the tarball — negligible against the existing `registry/dist` + `guildctl/dist` + `ui-dist` trees it ships beside (spec.md Assumptions).

**Constraints**: Per constitution Principle VII (Pluggable Stacks, Neutral Providers), the seeded default provider profile must not be vendor-specific — the generic OpenAI-compatible default (`https://api.openai.com/v1`, `OPENAI_API_KEY`) satisfies this more directly than either issue-offered direction (matching an undocumented `private-relay` default, or matching the previously-shipped DashScope docs) since neither of those is vendor-neutral. Per Principle VI (Fail-Closed Automation), `checkHarness`'s existing behavior of failing closed on a missing/unreachable adapter is correct and must not change — only the diagnostic's accuracy improves (US4). Per Principle V (Tests Before Production Code), every FR below is gated by a new or updated `migration/test/*.test.ts` case, listed per story.

**Scale/Scope**: Five targeted fixes — one packaging script (`scripts/build-dist.mjs`), one config module (`migration/guildctl/config.ts`), one harness module (`migration/guildctl/harness.ts`), two dead-file removals (`guildctl.config.json` root + `package/`) and their copy-reference cleanup, and five documentation files (`.env.example` ×2 identical copies, `README.md`, `GETTING-STARTED.md`, `DEVELOPMENT.md`) — plus `package/agent-shim.mjs` and `package/harness/opencode.mjs` for FR-015's DashScope-reference removal. Per FR-007, the grep surface is 15 existing test files (9 need genuine `DEFAULT_GUILD_CONFIG`-value assertion updates; the remaining 6 — including `evidence-runtime.test.ts`, `verification-state.test.ts` — match the grep on structural usage or an incidental literal and need no change but stay in the regression-run scope; see `tasks.md`'s T011–T020 for the authoritative per-file breakdown).

## Technical Approach Per User Story

### US1 — Tarball-only consumer reaches a working `guildctl` workspace (#148 Critical, FR-001..FR-003, SC-001)

**Module**: `scripts/build-dist.mjs`, `assembleTarball()` (lines 144–203).

**Current behavior**: `assembleTarball()` copies `migration/registry/dist` (line 188), `migration/guildctl/dist` (line 189), `migration/ui-dist` (line 190), and `stacks/` (line 191) into the tarball's `buildDir` — the comment at lines 181–187 explicitly documents this as the "self-contained kit" fix for a prior wave (#115/#123) but never extends to `migration/package.json`, `migration/package-lock.json`, or `migration/registry_schema.sql`. Verified: `migration/package.json` (dependencies `dotenv` 17.4.0, `better-sqlite3` 12.8.0, `commander` 12.1.0, `yaml` 2.8.1 — none bundled by `migration/tsup.config.ts`, which has no `noExternal`) and `migration/registry_schema.sql` are absent from every copy job in `assembleTarball()`. A tarball-only consumer following GETTING-STARTED.md step 4 (`cd migration && npm install`) hits `ENOENT` on a missing `package.json`; even if they somehow populated `node_modules` some other way, `migration/registry/db/schema.ts`'s `resolveSchemaPath()` (lines 5–19) would walk up 8 directories from `migration/registry/dist/db/` and never find `registry_schema.sql` on disk in the tarball, then fall back (line 18) to a path that also doesn't exist there.

**Change — add three copies to `assembleTarball()` (near lines 188–191)**: Add
```js
await fs.copyFile(path.join(repoRoot, "migration", "package.json"), path.join(buildDir, "migration", "package.json"));
await fs.copyFile(path.join(repoRoot, "migration", "package-lock.json"), path.join(buildDir, "migration", "package-lock.json"));
await fs.copyFile(path.join(repoRoot, "migration", "registry_schema.sql"), path.join(buildDir, "migration", "registry_schema.sql"));
```
placed alongside the existing `copyFilteredDirectory` calls (the `buildDir/migration` directory already exists by the time these run, since `copyFilteredDirectory` creates parent directories via `fs.mkdir(destinationDir, { recursive: true })` at line 122 for the sibling `registry/dist` copy). Per FR-002, these are `fs.copyFile` (verbatim), not passed through `copyFilteredDirectory`'s `.ts`-filtering logic (`shouldCopyPackageEntry`, lines 85–112) — that filter exists for `package/` (a source tree with `.ts` files that must not ship), not for these three already-final runtime files.

**Why not fold into `copyFilteredDirectory(migration, ...)` wholesale**: `shouldCopyPackageEntry` (line 103) currently excludes `topLevel === "migration"` entirely from the general `package/`-copy path — that exclusion is unrelated to this fix (it prevents `package/migration` from ever being considered, since `migration/` isn't nested under `package/`). Copying all of `migration/` wholesale would pull in `migration/*.ts` source, `migration/ui/` (a separate multi-hundred-file source tree with its own `node_modules`), and `migration/test/` — three explicit `fs.copyFile` calls for the three files GETTING-STARTED.md's documented flow actually needs is the minimal, correct fix, consistent with FR-002's "not a source tree for building" framing.

**Tests-first (FR-003, before the `assembleTarball()` edit)**:
- **NEW** `migration/test/build-dist-packaging.test.ts`, following `build-dist-docs-skip.test.ts`'s `stageKitRoot()`/`runBuildDist()`/`extractTarball()` pattern exactly (stage a temp kit root with `migration/node_modules` + `migration/ui/node_modules` + root `node_modules` copied in so `build-dist.mjs`'s own `npx tsup` / `npm run build:ui` steps can run for real, then execute the *staged* `scripts/build-dist.mjs` via `execFileSync`):
  - Case: after a successful `runBuildDist()`, extract the tarball and assert `migration/package.json`, `migration/package-lock.json`, and `migration/registry_schema.sql` all exist under `migration-guild-kit-build/migration/` in the extracted tree (fails on pre-fix code — this is the exact FR-003 requirement).
  - Case: `cd` into the extracted `migration/` and run `npm install --package-lock-only=false` (or assert the copied `package.json`'s `dependencies` block matches the repo's `migration/package.json` byte-for-byte, per FR-002 "MUST NOT rewrite") — proves FR-002's verbatim-copy requirement, not just presence.
  - Case (SC-001, live smoke test — may be marked slow/opt-in given `npm install`'s network dependency, matching the precedent that `build-dist-docs-skip.test.ts` already accepts long-running `tsup`/`vite` subprocess calls): after `npm install` completes in the extracted `migration/`, run `node migration/guildctl/dist/cli.js --help` and `node migration/registry/dist/cli.js list-artifacts` in a scratch workspace and assert both exit 0, with `list-artifacts` printing `[]`.

### US2 — Maintainer builds the dist from a fresh clone using only documented steps (#148 Critical, FR-004..FR-005, SC-002)

**Modules**: `scripts/build-dist.mjs`, `main()` (lines 205–236); `DEVELOPMENT.md`, "Build the repo" section (lines 131–143).

**Current behavior**: `main()`'s Step 1 (line 215–217) runs `npx tsup` with `cwd: migration/` (via `run("npx", ["tsup"], { cwd: path.join(repoRoot, "migration") })`), which requires `migration/node_modules` to already exist — `npx` will attempt to fetch `tsup` transiently only if it's not locally resolvable as a project dependency, but the real failure mode here is that `tsup`'s own compile needs `migration`'s `dependencies`/`devDependencies` (e.g. `@types/node`, `typescript`) present to type-check/bundle against. `DEVELOPMENT.md`'s "Build the repo" section (lines 131–143) documents only `npm run build` and `npm run build:dist` — the nested `migration/` and `migration/ui/` installs are documented solely in the unrelated "Run the repository test suites" subsection (lines 109–115: `(cd migration && npm install) && (cd migration/ui && npm install) && npm test`), which a maintainer following just "Build the repo" would never read.

**Change A — self-sufficient build (preferred direction, FR-004)**: In `main()`, before Step 1 (line 215), add a pre-install step that runs `npm install` (via the existing `run()` helper, which already resolves `npm`→`npm.cmd` on Windows and sets `shell: true` there — lines 18–24, 26–46) with `cwd: path.join(repoRoot, "migration")`, and similarly ensure `migration/ui`'s dependencies are installed before Step 3's `npm run build:ui` (line 227) — either as a second `run("npm", ["install"], { cwd: path.join(repoRoot, "migration", "ui") })` call, or folded into the root `npm run build:ui` script if that script already cascades (verify at implementation time; `migration/ui`'s own `package.json` scripts are out of this plan's read scope since FR-014 excludes UI code). `npm install` against an already-populated `node_modules` is a fast no-op (spec.md Edge Cases), so this is safe to run unconditionally on every `build:dist` invocation — no idempotence guard needed.
- **Fallback direction (if the preferred direction proves impractical during implementation)**: pre-check `fs.existsSync(migration/node_modules)` and `fs.existsSync(migration/ui/node_modules)` before Step 1, and `throw` a single actionable error naming all three install locations (root, `migration/`, `migration/ui/`) if either is missing — mirroring the existing `main().catch()` error-surfacing pattern (lines 238–242).

**Change B — DEVELOPMENT.md (FR-005)**: Add a line to the "Build the repo" section (before or alongside the existing `npm run build` / `npm run build:dist` code block, lines 135–138) stating all three install locations (root `npm install`, `cd migration && npm install`, `cd migration/ui && npm install`) up front — either because Change A makes the nested installs automatic (in which case the doc states that fact, so a maintainer understands why `build:dist` "just works"), or because the fallback pre-check needs the doc to match its own error message.

**Tests-first (before the `main()` edit)**:
- **NEW** `migration/test/build-dist-nested-install.test.ts`: stage a temp kit root the same way `build-dist-docs-skip.test.ts` does, but this time deliberately *omit* `migration/node_modules` and `migration/ui/node_modules` from the staged copy (skip the two `fs.cpSync` calls that `stageKitRoot()` currently performs for them) while still providing the root `node_modules` (so `npm`/`npx` themselves are resolvable). Assert:
  - Case (Change A path): `runBuildDist()` against this stripped-down staged kit still exits 0 and produces a tarball (proving the build now self-installs).
  - Case (Change A path, regression): `npm install`'s own network/timing variance is mitigated by asserting `migration/node_modules/dotenv` (or another leaf dependency) exists in the *staged temp kit* after the run, not just that the tarball was produced — closing the gap where a silently-skipped install could still coincidentally produce a tarball from stale prior artifacts.

## Risks & Open Questions

**Risks**
- **US1 — verbatim-copy drift**: `migration/package.json`'s `dependencies` (dotenv, better-sqlite3, commander, yaml, `@modelcontextprotocol/sdk`) must stay copyable as-is; if a future change makes `migration/package.json` reference a `file:`-relative or workspace-relative dependency that only resolves inside the monorepo (not from a standalone tarball `migration/`), the verbatim-copy strategy would break silently until someone runs the SC-001 smoke test. Mitigation: the new `build-dist-packaging.test.ts`'s live-`npm install`-and-smoke-test case is exactly the guard against this class of drift, and should not be skipped in CI even though it's slower.
- **US2 — self-install must not mask a genuinely broken clone**: if `npm install` in `migration/` or `migration/ui/` itself fails (e.g. a genuinely broken lockfile), the added pre-install step must propagate that failure loudly via the existing `run()` helper's rejection (which `main().catch()` already surfaces, lines 238–242) rather than being wrapped in a try/swallow — consistent with the existing precedent for the UI build step (`main()` lines 223–227's comment: "Not wrapped in a try/swallow... the same way a failed tsup step does").
- **US3 — model-identifier choice is a genuine open design decision**: FR-006 pins the *shape* (OpenAI-compatible base_url + api_key_env + model id) but not the exact literal model id for `model.model`/`provider.routes`/`agents.*.model`. This plan defers the exact string(s) to implementation/tasks, consistent with how the 011 plan deferred US2's exact packaging mechanism and US3's exact error wording as open questions rather than blocking decisions.
- **US4 — fixture-to-branch mapping for the two existing wording assertions**: both `harness-selection.test.ts:32` and `doctor-pipeline-state.test.ts:319` use a nonexistent-path fixture with `source` set such that they hit the **spawn-error** branch, not the non-zero-exit branch this story's headline scenario (Copilot CLI not installed) targets — implementation must confirm this mapping (via `spawnSync`'s actual `result.error` vs `result.status` behavior for a nonexistent executable on the target platform) before writing the exact updated regex, since a wrong branch assumption would make the "regression" update accidentally test the wrong code path.

**Open Questions**
- US2's exact self-install mechanism (a dedicated pre-install step per nested directory vs. folding into existing `run:ui`/root scripts) is deferred to implementation/tasks — both satisfy FR-004, and the choice is an implementation detail.
- US3's exact OpenAI-compatible model identifier(s) for `model.model`, `provider.routes`, and `agents.*.model` are deferred to implementation/tasks — FR-006 constrains provider/credential/base_url, not the specific model string.
- US4's exact HARNESS_OUTPUT_CAP reuse-vs-local-constant decision (reuse `runner.ts`'s existing `HARNESS_OUTPUT_CAP = 512`, or define a smaller `--version`-probe-specific cap per spec.md's "~200 chars is plenty") is deferred to implementation — FR-008 requires "trimmed, length-capped," not an exact number.
- US5's FR-013 MVP-vs-incremental choice (doc-only note vs. `setup.ts` EOF handling) is explicitly left open by the spec itself ("the docs note is the MVP, the readline fix is incremental" — spec.md Edge Cases); this plan defaults to the MVP (doc-only) scope unless `tasks.md` elects to include the incremental fix.

## MVP vs Incremental Boundaries

US1 and US2 are the P1/Critical MVP core: without them, the tarball is not installable and the build is not reproducible from documented steps — nothing else in the kit matters until these land (spec.md's own "Why this priority" framing for both stories). US3 (P3) and US4 (P4) are Medium-severity guidance fixes that do not block reaching a running workspace (a fresh `init` still succeeds; `doctor` still fails closed) but each closes one specific "user hits a wall with zero explanation" gap — both are still in-scope for this feature (the spec lists no deferred story), just lower priority within it. US5 (P5) is pure documentation plus two dead-file deletions, sequenced last because it has no runtime impact; within US5, FR-013's `setup.ts` EOF-handling half has an explicit spec-sanctioned MVP/incremental split — this plan's default scope takes the doc-only MVP (a GETTING-STARTED.md note) and treats the `setup.ts` readline fix as an incremental addition `tasks.md` may or may not pick up, per spec.md's explicit instruction not to let this expand into a general stdin-automation feature (no new flags, no scripted-answer API). All five user stories, at whatever FR-013 scope is chosen, together satisfy SC-001 through SC-005 — there is no user story deferred to a future wave; FR-014's boundary (no registry/claims/evidence-gate/arbitration/audit-rule/UI changes) is the feature's outer edge, not an internal MVP/incremental split.
