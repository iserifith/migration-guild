# Data Model — Wave 1 Workspace Source-of-Truth (Onboarding Hardening)

Generated by `$speckit-plan` Phase 1. Entities are filesystem/runtime artifacts of the
Migration Guild workspace, not a relational schema (this feature is tooling/onboarding,
not a new data store). Validation rules and state transitions are expressed as
workspace-layout invariants the implementation must enforce.

## Entities

### 1. Migration Workspace (the self-contained unit)

The directory produced by `setup.ts` — the single, independently-runnable source of truth
for running a migration. After this change it contains, at minimum:

| Path | Source | Required | Notes |
|---|---|---|---|
| `legacy/` | user | no | User's read-only source (constitution §II). |
| `modern/` | setup scaffold | yes | Migrated output target. |
| `migration/` | kit `migration/` tree (built `dist/`) | **yes** | The runtime. `migration/dist/guildctl/cli.js` must exist for the smoke test. Previously NOT in the tarball kit (#115). |
| `package/` | kit `package/` | yes | Agents, skills, prompts, instructions, harness shim. |
| `stacks/` | kit `stacks/` | yes | Stack packs. |
| `harness/` | kit `harness/` | yes | Agent harness launchers. |
| `.github/agents`, `.github/skills`, `.github/prompts`, `.github/instructions` | kit `package/` | yes | Shipped agent artifacts. |
| `.guild/config.yaml` | `guildctl init` | **yes** | The ONE config source of truth (FR-005). |
| `.guild/registry.db` | runtime | no | Workspace-local registry; never in the kit. |
| `.env` / `.env.example` | kit | yes | Credential env. |
| `guildctl.config.json` | — | **no (removed)** | Was an orphan; deleted from kit + setup output (FR-005/FR-007). |

**Validation rules (post-change):**
- `migration/dist/guildctl/cli.js` exists after setup (kit-bundled built runtime) → enables `node migration/dist/guildctl/cli.js --help` with no checkout (FR-001, SC-001).
- Exactly one config file is both documented and read: `.guild/config.yaml`. No orphan
  `guildctl.config.json` remains in the workspace or kit (FR-005, SC-004).
- `.guild/` is workspace-local; two workspaces resolve distinct config + registry paths
  (FR-009, existing test at `workspace-isolation-defaults.test.ts:74` preserved).

### 2. Guild Config (`.guild/config.yaml`)

Authoritative, workspace-local config loaded by the runtime. The runtime contract is
unchanged — it already reads only this file. The change is *documentation + removal of the
competing JSON file*, plus ensuring `init` writes it without a toolkit-root dependency.

**Schema (subset the user edits — from `DEFAULT_GUILD_CONFIG`):**
```yaml
profiles:
  default:
    base_url: "https://example-private.invalid/v1"   # OpenAI-compatible endpoint
    model: "pvt/hy3-tencent"
    api_key_env: "EXAMPLE_PRIVATE_API_KEY"
harness: "opencode"                         # top-level harness selector
model:
  model: "pvt/hy3-tencent"
  base_url: "https://example-private.invalid/v1"
  api_key_env: "EXAMPLE_PRIVATE_API_KEY"
database:
  path: ".guild/registry.db"
```

**Validation rules:**
- GETTING-STARTED.md must instruct edits to exactly these keys (`.guild/config.yaml` →
  `profiles.default.base_url` / `api_key_env` / `model` and top-level `harness:`) — replacing
  the incorrect `guildctl.config.json` guidance (FR-007, SC-002).
- Edits to `.guild/config.yaml` MUST change `guildctl config` output (FR-006) — already true
  today; the doc fix makes it reachable.

### 3. Kit / Distributable (tarball)

Assembled by `scripts/build-dist.mjs`. After this change it MUST include a pre-built
`migration/` runtime so tarball users receive it without a separate build (FR-011).

**Assembler additions (implementation detail, pinned by research Decision 4):**
- Copy `migration/dist/` (built CLIs) into the kit's `migration/` so the tarball carries a
  runnable runtime.
- Stop referencing/bundling `guildctl.config.json`.

### 4. Toolkit-Root Layout (deprecated concept)

The previous assumption that an initialized workspace must sit beside a
`package/`+`stacks/`+`migration/` source checkout, and that `init` symlinks those dirs into
the workspace from the sibling root. This requirement **removes** that assumption: the
workspace IS self-contained, so `init` must not require or create toolkit-relative links
(Decision 3, FR-003/FR-004).

## State transitions

| Transition | Trigger | Pre-state | Post-state | Invariant |
|---|---|---|---|---|
| Setup (install) | `node setup.js` in clean dir | empty dir + kit | self-contained workspace | `migration/dist/guildctl/cli.js` present; no `guildctl.config.json` |
| Init | `guildctl init` | workspace w/o `.guild/config.yaml` | `.guild/config.yaml` created, local dirs untouched | no toolkit-link requirement; idempotent |
| Init (re-run) | `guildctl init` (no `--force`) | workspace w/ config | config preserved | existing config not overwritten |
| Update | `node setup.js --update` | existing workspace | kit files refreshed | `registry.db`, `legacy/`, `modern/`, `.guild/config.yaml` preserved (FR-010) |
| Tarball extract | `tar -xzf kit.tar.gz` | clean dir | kit tree w/ built `migration/` | `migration/dist/guildctl/cli.js` present without build |

## Cross-cutting invariants (constitution)

- §II Legacy read-only: `legacy/` is never written by setup beyond user copy/clone.
- §Repository Source-of-Truth Boundaries: kit = source; installed workspace = standalone.
  The kit must therefore *contain* a built runtime, not expect one to be built by the user
  post-extract (closes #115 for the tarball path).
- §V Tests before production code: contract/behavior changes to `scaffoldWorkspaceLinks`
  and the removed `guildctl.config.json` must ship with updated regression tests (the
  amended `workspace-isolation-defaults.test.ts` and a new doc-follows-config test).
