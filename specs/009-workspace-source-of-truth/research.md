# Research — Wave 1 Workspace Source-of-Truth (Onboarding Hardening)

Generated by `$speckit-plan` Phase 0. Resolves every `NEEDS CLARIFICATION` from the
Technical Context and records the decisions that drive the Phase 1 design.

All findings below were verified by reading the current repo state on branch
`spec/issue-130` (post-specify), not assumed.

## Decision 1 — Configuration source of truth is `.guild/config.yaml`

- **Decision:** `.guild/config.yaml` is the single, authoritative, workspace-local
  configuration file. The orphan root `guildctl.config.json` is removed from setup
  output, from the kit source, and from `benchmark.ts` scaffolding; docs are corrected
  to point at `.guild/config.yaml`.
- **Rationale:** `migration/guildctl/config.ts` only ever reads `.guild/config.yaml`
  (`guildConfigPath()` → `path.join(root, ".guild", "config.yaml")`;
  `resolveGuildConfig` / `readGuildConfig`). The root `guildctl.config.json` is written
  by `setup.ts` (line 202) and copied by `benchmark.ts` (line 92) but is **never loaded**.
  Making the JSON file authoritative would require wiring a second loader + precedence
  rules; removing it is strictly simpler and eliminates the "two files, one dead" ambiguity
  that the black-box test (F6) reproduced. This satisfies FR-005/FR-006/FR-007.
- **Alternatives considered:** (b) make `guildctl.config.json` authoritative and load it.
  Rejected — more code, more precedence ambiguity, and it diverges from the now-stable
  `.guild/config.yaml` loader that the rest of the runtime depends on.

## Decision 2 — Adopt option (a): self-contained workspace

- **Decision:** The workspace produced by `setup.ts` is a complete, independently-runnable
  thing: it contains its own `migration/` runtime, `package/` (agents/skills/prompts/
  instructions), `stacks/`, `harness/`, `.github/`, and `.guild/config.yaml`. `init` and
  config resolution are fully workspace-local; there is no requirement for a sibling
  toolkit-root checkout.
- **Rationale:** This is the issue's stated goal and aligns with constitution §Repository
  Source-of-Truth Boundaries (the kit is source; an installed workspace must stand alone).
  Option (b) ("workspace lives beside a checkout") was explicitly available but rejected
  because it keeps `init`/setup fragile for kit/tarball users — the exact population the
  onboarding test targets.
- **Alternatives considered:** (b) redefine "workspace" as "lives beside a checkout" and
  fix docs/wizard to match. Rejected — does not produce a self-contained workspace and
  leaves kit/tarball users unable to run without cloning the repo.

## Decision 3 — `scaffoldWorkspaceLinks` must be workspace-local, not toolkit-relative

- **Decision:** `scaffoldGuildConfig` must NOT assume a sibling toolkit-root. It should
  treat `migration/`, `package/`, `stacks/` as *already present in the workspace* (because
  `setup.ts` copies them) and **skip linking** when those directories exist locally.
  The link/symlink path (`scaffoldWorkspaceLinks`) becomes a **fallback only** for the
  legacy "run guildctl inside the toolkit checkout" scenario, and must never throw a
  cryptic "missing toolkit target" error when the workspace is already self-contained.
- **Rationale:** `scaffoldWorkspaceLinks(root)` does `ensureLinkOrJunction(root/<name>,
  toolkitRoot/<name>)`. For a self-contained workspace, `root/migration` already exists as a
  real directory (copied by setup), so the link attempt hits
  `ensureLinkOrJunction`'s "already exists and points to…" branch and throws — this is the
  #114 failure ("`guildctl init` requires a toolkit-root layout"). Removing the hard
  requirement satisfies FR-003/FR-004.
- **Contract impact (explicit):** This changes behavior pinned by
  `migration/test/workspace-isolation-defaults.test.ts` lines 54–67, which asserts that
  `init` creates symlinks `migration`/`package`/`stacks` pointing *into the toolkit
  checkout*. Under the self-contained model that assertion is no longer correct: a workspace
  that already contains those dirs must NOT be re-linked. That test MUST be amended in the
  implement phase (replace the "links into checkout" expectation with "workspace-local dirs
  are left intact / not re-linked, and toolkit-fallback links only occur when absent"). This
  is a sanctioned, documented contract change, not an accidental regression.

## Decision 4 — The kit/distributable must bundle a built `migration/` runtime

- **Decision:** `scripts/build-dist.mjs` assembles the tarball. It currently copies
  `package/`, docs, and `setup.js` but **does not** include a built `migration/` runtime.
  The assembler must copy the already-built `migration/dist/` (and the `migration/` source
  needed by `setup.ts`'s `tools` mapping) into the kit so a tarball-extracted workspace has
  `migration/dist/guildctl/cli.js` without a separate build step.
- **Rationale:** `setup.ts` copy step for `tools` → `migration/` works *only if the kit
  already contains a `migration/` tree to copy from*. In the dev-checkout run path,
  `migration/` exists; in the distributed-tarball path it currently does not. This is the
  #115 gap for kit/tarball users. Satisfies FR-001/FR-002/FR-011.
- **Note:** `setup.ts` already copies `migration/` in **both** install and `--update`
  (ROOT_MAPPINGS.tools + the `runUpdate()` `tools` block, both skip `node_modules` and
  `registry.db`). So the in-workspace copy logic is fine; the missing piece is the *kit
  assembly* bundling a built runtime. No change needed to `setup.ts`'s copy mechanics for
  #115 beyond confirming the kit provides the source tree.

## Decision 5 — `init` is idempotent and config-preserving

- **Decision:** `guildctl init` (`scaffoldGuildConfig(root, force)`) already preserves an
  existing `.guild/config.yaml` unless `--force`. The plan keeps that and adds: do not
  clobber the user's `migration/`/`package/`/`stacks/` (they are legitimately workspace-local
  now). `--update` in setup preserves `registry.db`, `legacy/`, `modern/`, and
  `.guild/config.yaml` (already the case in `runUpdate()`). Satisfies FR-010.

## Decision 6 — Two workspaces must not cross-contaminate

- **Decision:** Config already resolves from the workspace's own `.guild/` via
  `findGuildRoot` walking up from cwd, and the registry defaults to `.guild/registry.db`
  (workspace-relative). No code change required for FR-009 beyond not re-linking into a
  shared toolkit root (Decision 3 removes that coupling). The existing
  `two initialized workspaces write to distinct local registry databases` test (line 74)
  remains valid and is preserved.

## Open items handed to implement/tasks phase

- Exact `setup.ts` wording for the "Next steps" block (it currently tells users to
  `cd migration && npm install && npm run build` — fine for dev-checkout, but the kit user
  already has `migration/dist/`, so the build step should be conditional / documented as
  optional). Implementation detail, not a design decision.
- Whether `benchmark.ts` should still emit `guildctl.config.json` — Decision 1 says remove;
  benchmark's copy is dead weight and will be dropped there too.
- Whether to keep `guildctl.config.json` as a documented *schema example* anywhere — no; the
  authoritative schema already lives in `DEFAULT_GUILD_CONFIG` / `.guild/config.yaml`. The
  docs will reference that schema directly.
